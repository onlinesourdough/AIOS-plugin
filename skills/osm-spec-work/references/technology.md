# Resolve a material technology decision

Use only for a new or materially changed capability after the Spec has resolved
responsibilities and constraints. Keep a sufficient working stack. Name the
owner, source of truth, interfaces and trust boundary, then compare plausible
Build, Buy, Rent or Self-host options. Reuse existing capabilities; a starter's
database, queue or runtime is not evidence that the outcome requires it.

Check dated official sources for decision-changing contracts, license, plan
limits/cost, maintenance, failure/recovery and exit paths. Self-hosting needs an
operator for security, updates and restore; a managed dependency still needs
failure and replacement ownership. Prefer a cohesive unit unless ownership,
deployment, scaling, isolation or recovery must be independent. Keep reusable
deterministic behavior replayable outside an orchestration vendor.

When low cost or usage determines the choice, model realistic initial usage and
the compute, storage, egress or API boundary that can create an overage. Compare
only viable shapes and name the observer, guardrail, stop condition and exit
path. Do not copy volatile price tables or invent savings.

Record the selected capability, fit, operating burden, material risks,
verification and update/exit path in existing repository truth. A concrete
specialist gap uses available local or installed capabilities; acquisition
requires its own authority. Continue Build without a second discovery interview.
